Every design system starts as two buttons and a color. Then the third product arrives, the fourth designer joins, and suddenly there are eleven shades of gray. Systems do not fail from lack of components — they fail from lack of decisions.

## Tokens before components

Agree on the primitives first: spacing scale, radius, color roles (not color values), type scale. Components built on shared tokens stay consistent for free. Components built on hex codes drift within months.

## Document the why, not just the what

A prop table tells me what a button accepts. It does not tell me when to use a ghost button versus a primary one. The most valuable page in any design system is the guidance page nobody wants to write.

## Version like an API

Removing a prop is a breaking change. Treat the system as a dependency: changelog, migration notes, deprecation warnings. Your consumers are teammates — give them the same respect you give external users.

A design system that scales is not the one with the most components. It is the one with the clearest decisions.
